# ADR-0034: Database Engine per Deployment

**Date:** 2026-11-16

## Status

Accepted

## Context

Version 1.0.0 ships Cauce first as a desktop app for people who are not
technical: they download an installer, open the app, create their local
profile and start. The installer carries the API, the web client and the
database. Nothing can depend on a database server the learner installs or
starts by hand, and the data on disk has to be encrypted, because a laptop is
easier to lose or share than a server.

Every other way of running Cauce keeps a server: local development, the Docker
setup for self-hosting (ADR-0019) and a hosted version later. Those already
run on PostgreSQL, with 19 migrations written in PostgreSQL SQL.

Three ways of bundling a database into the desktop app were compared:

| Option | What it means for the desktop app |
|---|---|
| PostgreSQL binaries started by the app | A full PostgreSQL server per platform inside the installer, started and stopped by the app. Upgrading PostgreSQL across app versions needs a dump and restore of the learner's data |
| PostgreSQL compiled to WebAssembly, running inside the API process | The same SQL dialect, but a single connection and an ORM driver maintained outside the ORM project |
| SQLite with an encryption extension | A single file, no server process, widely used by desktop apps, encryption built into the driver. A second SQL dialect to support |

The current code was checked for how much it depends on PostgreSQL:

| Dependency | Where |
|---|---|
| `jsonb` and `text[]` columns | The user entity: `intake`, `enabledModules`, `widgetConfig` |
| `timestamp` and `timestamptz` columns | Most entities |
| Raw SQL with `$1` placeholders and a `::int` cast | Topics with their resource count |
| Trigram similarity (`similarity()`, `pg_trgm`) | Similar titles when capturing a resource |
| `LOWER()` that understands accents | Topic deduplication, ordering and title search |
| `UNIQUE`, `CHECK` and foreign key constraints | Only in the PostgreSQL migrations, not in the entities |

Identifiers are UUIDs generated by the domain, not by the database, so they
already work the same on any engine. No repository test runs against a real
database today: repositories are covered through mocks.

## Decision

### Each deployment uses one engine

- **Desktop app:** SQLite through `better-sqlite3-multiple-ciphers`, which
  encrypts the whole file (pages, journal and WAL) with a SQLCipher-compatible
  cipher.
- **Everything else** (development, self-hosting, hosted): PostgreSQL, as
  today.

The API reads `DB_TYPE` at startup (`sqlite` or `postgres`, PostgreSQL by
default). One running API uses one engine; nothing syncs between them.

### Entities are shared; column types come from one map per engine

There is one set of entities. Entities never name an engine type: the columns
whose type depends on the engine declare a logical type instead, and each
engine provides its own map from logical types to its column types.

`infrastructure-lib` defines the logical types as a `ColumnTypes` interface and
one implementation per engine:

| Logical type | Meaning | PostgreSQL | SQLite |
|---|---|---|---|
| `dateTime` | A date and time with no time zone | `timestamp` | `datetime` |
| `instant` | An exact moment, stored in UTC | `timestamptz` | `datetime` (UTC text) |
| `structured` | A structured value | `jsonb` | `simple-json` |
| `stringList` | A list of strings with a default | `text[]` | `simple-json` |

The engine is chosen in a single place, which exports the map for the engine
in use; entities read `columnTypes.instant`, `columnTypes.structured` and so
on. Each map must implement the whole interface, so a logical type added for
one engine fails to compile until the other engine provides it too. A third
engine would be one more map, with no change to the entities.

Entity decorators run when their module is imported, before the application
starts, so the map cannot come from the injected configuration. It is chosen
from `DB_TYPE` in the process environment, which has to be set before any
entity module loads: the desktop shell sets it when it starts the API, and in
development it comes from the environment file loaded at startup.

### Two migration folders

- `migrations/postgres/` holds the existing 19 migrations, unchanged.
- `migrations/sqlite/` starts with a baseline that creates the current schema
  in one step, including every `UNIQUE`, `CHECK` and foreign key constraint
  that today exists only in the PostgreSQL migrations.
- From then on, every schema change ships one migration per engine in the same
  pull request.
- Schema synchronization from the entities is never used, on either engine.

The desktop app runs pending migrations when it starts, before the window
opens.

### Engine differences live in the connection, not in the repositories

Repositories do not branch on the engine. Where SQLite lacks something
PostgreSQL provides, the SQLite connection supplies it when it opens:

- `lower()` is replaced by a version that lowercases accented letters too, so
  "Álgebra" and "álgebra" match and sort together, as in PostgreSQL.
- `similarity()` is registered as a function that computes trigram similarity
  in the API process. A single learner's titles are few enough for this to
  stay fast without an index.
- Temporary data stays in memory (`temp_store = MEMORY`), so sorting and
  intermediate results never reach the disk unencrypted.

Raw SQL in repositories may only use syntax both engines accept. The topic
count query moves to the query builder; the similar-titles query keeps its
SQL and drops the `$n` placeholders for the query builder's named parameters.
Values that come back from raw SQL are converted in `toDomain`, since SQLite
returns dates as text.

### Repository tests run on both engines

A repository test layer is added that runs each repository against a real
database: PostgreSQL in a CI service container and SQLite in a temporary file.
Both run on every pull request that touches an entity, a repository or a
migration. This is where the differences listed above are caught, instead of
on a learner's machine.

### The database key comes from the desktop shell

On desktop the API never reads the database key from the environment. The app
shell generates a random 256-bit key on first launch, keeps it protected by the
operating system's keystore and hands it to the API over the channel between
the two processes. How a recovery key and backups protect that key
belongs to the local access mode in ADR-0020 (revision 2026-11-17).

## Consequences

**Positive**

- The desktop app needs no server process and no setup: the database is one
  encrypted file in the app's data folder.
- Self-hosting, development and a future hosted version keep PostgreSQL and
  everything already written for it.
- Domain and application code do not change: the difference stays inside
  infrastructure, behind the repositories.
- Repository tests against real databases cover queries that mocks never
  checked, on both engines.

**Negative**

- Every schema change is written twice, once per dialect, and reviewed twice.
- The SQLite baseline has to reproduce constraints that today live only in
  PostgreSQL SQL; a constraint missed there is a rule the desktop database
  silently does not enforce.
- New raw SQL has to be checked against both dialects, and the CI run gets
  longer with the second engine.
- Moving a learner's data from the desktop app to a hosted account later needs
  an export and import step; the two databases cannot be copied file to file.

## Open Questions

- The export format a learner uses to back up their data or move it to another
  installation.

## Rejected Alternatives

- **Building entity schemas at runtime instead of with decorators:** TypeORM
  can describe entities as schema objects created while the application
  starts, which would let the engine arrive through injected configuration
  like every other setting. It means rewriting every entity and its mapping,
  for a gain that only matters at import time; the column type map covers the
  same need.

- **PostgreSQL binaries started by the app:** keeps one dialect, but adds a
  server process to manage on the learner's machine, a larger installer per
  platform, and a dump and restore every time the bundled PostgreSQL major
  version changes. Encryption at rest would need an extra layer on top.
- **PostgreSQL compiled to WebAssembly:** keeps one dialect without a separate
  process, but depends on an ORM driver outside the ORM project, allows a
  single connection, and was the least proven of the three for a desktop app
  that has to keep working across updates.
- **SQLite everywhere:** one dialect again, but a hosted version serving many
  learners needs concurrent writers and the features the PostgreSQL schema
  already relies on.
